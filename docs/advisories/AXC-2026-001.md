# AXC-2026-001 · Consent transitions accepted without authentication

| | |
|:--|:--|
| **Severity** | Critical |
| **Affected** | `axonos-consent` ≤ 0.8.0 |
| **Fixed in** | 0.9.0 |
| **Specification** | Consent Specification ≤ 0.5.0, §7.2; fixed in 0.6.0 |
| **Published** | 2026-10-02 |

## Summary

`ConsentMachine::handle_event()` admitted a consent transition when a 4-byte
field of the record matched a value computed from the record and the trusted-path
**public** key. A public key is not a secret. Anyone who knew it could compute
the value for any record they liked, and so could withdraw, suspend or resume
consent at will. The full Ed25519 verification the specification required was
described as happening "out of band" and was never performed by the crate.

## Impact

Any party able to deliver bytes to the consent path could:

- **resume** a suspended installation, so that observations flow without consent;
- **suspend** or **withdraw** it, denying service to the person it protects.

`DualControlMachine` was affected in the same way: both halves of a
co-authorisation could be forged, and the co-authorisation window ran on a
timestamp the sender chose. No version replay-protected its frames, so even a
genuine frame could be resent at will.

## Fix

0.9.0 replaces the wire format with version 2: a 32-byte record followed by its
64-byte Ed25519 signature (RFC 8032), verified under strict rules before any
field of the record is acted on. An unforgeable type, `Authenticated`, is the
only input the machines accept. Every frame carries a sequence number that must
increase per signer and survives a power cycle. Under dual control the role is
signed, the two keys must differ, and the window runs on the kernel's clock.

Kani proves that a frame whose signature does not verify changes nothing, and
that no sequence number is admitted twice.

## Workaround

None. A deployment cannot make the 0.8.0 check sound; upgrade to 0.9.0.
